# Antigravity prompt: EdgeTrust performance evaluation

Paste everything below into Antigravity as the project brief. Attach the
CICIoT2023 CSV files (or a folder containing them) as the dataset, and
attach or upload the `edgetrust_pipeline/` folder from this delivery as
the starting codebase, before running the agent.

---

## Context

I am implementing and evaluating **EdgeTrust**, an edge-native IoT trust
management framework described in an academic manuscript. EdgeTrust has
two layers: Layer 1 is a LightGBM classifier that gates traffic as
benign or malicious; Layer 2 computes a bounded composite trust score
from six equations (Shannon entropy weighting, a normalized weighted-sum
trust score, a Holt linear-trend forecast, a sigmoid-gated adaptive
threshold, and a three-state hysteresis controller with a 3-epoch
promotion-confirmation rule), and an ABAC-style policy layer turns the
resulting trust state into an access decision.

I have already written a working Python implementation of this pipeline
(the `edgetrust_pipeline/` folder attached to this project). It has been
syntax-checked and smoke-tested end to end against a small synthetic CSV
matching CICIoT2023's real column schema, but it has **never been run
against the real CICIoT2023 dataset**, because it was built in an
environment without access to it. That real run is your job.

## Dataset

CICIoT2023 (Neto et al., 2023, *Sensors*, doi: 10.3390/s23135941): 105
IoT devices, 33 attacks across 7 categories (DDoS, DoS, Recon, Web-based,
Brute Force, Spoofing, Mirai), 47 features per flow, ~46-47 million rows
across ~169 CSV files, heavily class-imbalanced. I am attaching the CSV
files directly. Place them under `edgetrust_pipeline/data/CICIoT2023/`
if they are not already there (subdirectories are fine, the loader
searches recursively).

## Your task, in order

1. **Verify the environment.** Install `edgetrust_pipeline/requirements.txt`.
   Confirm the attached CSVs load via `src/data_pipeline.load_ciciot2023`.
   If column names or label strings differ from what `config.py` assumes
   (`config.RAW_FEATURES`, `config.LABEL_TO_CATEGORY`, `config.LABEL_COL`),
   fix the mismatch in `config.py` rather than working around it deeper
   in the pipeline; print and inspect a sample of the real label column
   first so the fix is based on what's actually there, not a guess.

2. **Run a fast subsample first.** `python run_all.py --sample-frac 0.02`
   (or `--max-rows-per-file`). Fix any errors that come up before moving
   to a larger run. Do not silently swallow exceptions or fall back to
   placeholder numbers, if something fails, the run should fail loudly so
   I know to look at it.

3. **Run the full dataset** once the subsample run is clean, unless the
   compute/time budget genuinely doesn't allow it, in which case use the
   largest subsample that does and say so explicitly in the final report.

4. **Sanity-check the results before reporting them.** Specifically:
   - Theorem 1 (entropy weight validity) must hold exactly; if it
     doesn't, that's a bug in `entropy_weights.py`, not a result to report.
   - Theorem 5's corrected bound (Scenario E) must hold in 100% of trials
     by construction; if it doesn't, stop and debug rather than reporting
     a violated "proof."
   - If Scenario B's ablation shows the full pipeline with a much higher
     state-flap count than the static-threshold baseline, that's
     backwards from what the mechanism is supposed to do (the hysteresis
     and forecasting should *reduce* flapping relative to a static
     threshold on real signal); treat that as a bug to investigate, not
     a number to report as-is.
   - If Scenario A's accuracy is at or near 50% (chance level) on the
     real data, that likely means the label mapping or feature selection
     is broken, not that the method doesn't work, check
     `config.LABEL_TO_CATEGORY` coverage and the top-14 feature list
     before concluding anything about EdgeTrust's performance.

5. **Extend Scenario F** (the baseline comparison) if time allows: the
   current candidate set (Random Forest, XGBoost, logistic regression as
   a linear-threshold analogue, a simple ELM) is a starting point, not
   the full "fifteen competitive baselines" the manuscript's Abstract
   references. Add more candidates from the manuscript's Related Work
   section if you have access to it, keeping every candidate on the
   identical 14-feature training and test sets so the comparison stays
   fair.

6. **Produce the final report** as `outputs/report.md` (already
   auto-generated by `run_all.py`) plus every figure in `outputs/figures/`
   and every table in `outputs/tables/`. At the top of the report, add a
   short section stating: how much of the dataset was used (sample
   fraction or full), total wall-clock run time, and the hardware this
   ran on (CPU model, RAM), since the latency and throughput numbers are
   only meaningful with that context attached.

## Hard constraints

- **Never fabricate a result.** If a scenario fails to run (missing
  column, out-of-memory, a model that won't converge), report the
  failure and what you tried, don't paper over it with an invented
  number that looks plausible.
- **Don't change the six equations** in `trust_engine.py` to make the
  numbers look better. If a real result is disappointing (low accuracy,
  high latency, more state flaps than expected), that is itself useful
  and reportable information, not a bug to hide by quietly loosening a
  threshold or adding a fudge factor. If you do suspect an actual
  implementation bug (not just an unflattering result), fix it, and say
  explicitly in the report what was wrong and what changed.
- **Keep the caveats.** The code already labels certain things
  explicitly (the lack of a real device/session ID, the feature
  direction assumptions, the illustrative nature of Scenario C's
  sessions). Preserve those caveats in the final report rather than
  presenting every number as unconditional ground truth.
- **Cite what you use.** If you add any baseline method, dataset
  variant, or library beyond what's already in `requirements.txt`, name
  it explicitly in the report so it can be cited properly in the
  manuscript.

## Deliverable

A completed `outputs/` folder (figures, tables, report.md) from a real
run against the attached CICIoT2023 data, plus a short summary at the
top of the report of exactly what was run, on what data, on what
hardware, and how long it took.
